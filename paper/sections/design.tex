\section{Design}
\label{sec:design}

\sys{} is a userspace ANNS runtime plus a thin residency plane in front of
host DRAM, a bounded window that plays the role of CXL-DRAM, and a
flash-backed CXL address space that holds $D$
(Figure~\ref{fig:design-arch}). Search is still best-first graph walk.
The service contract is a \emph{split}: prefetch and continuous
batching may touch CXL-SSD; the scoring thread may not. A hop that
computes a full-precision distance from bytes that were not already in
the window is a hide failure, not a successful promote.

One walk cannot fully hide hop $i{+}1$ until hop $i$ scores
(pointer-chasing). Intra-query hide is lookahead of the current
frontier only. Inter-query continuous issue is what keeps device depth
up while a single walk is stuck. We do not claim the measured prototype
has met this contract~(\S\ref{sec:eval}); the modules below are the
mechanisms that must.

\subsection{D1: Semantic placement}
\label{sec:d1}

Table~\ref{tab:placement} is the default map. The graph adjacency and the
PQ codebook are touched on every hop and are small relative to the
full-precision corpus; they live in host DRAM so they never compete with
vectors for the CXL-SSD window (F2, F7). Query state (candidates, visited
set, thread-local arenas) is likewise host-local. Full-precision vectors
default to the CXL-SSD address space. A bounded \emph{hub / shared hot
set} of records is explicitly cached into the window or into CXL-DRAM
(\S\ref{sec:d3}). Frontier-top neighbors are candidates for precise
promotion, not for bulk 2-hop prefetch (F3).

This is a deliberate difference from DiskANN, where adjacency and vectors
share SSD sectors. We pay a modest host-DRAM tax for the graph in order
to stop the window from turning into an accidental adjacency cache.

\subsection{D2: Bounded precise promotion}
\label{sec:d2}

Promotion is an explicit \texttt{promote(ids[], level, budget)} on the
residency plane (Figure~\ref{fig:design-promote}). The only ids that
enter the call are the neighbors of the \emph{current frontier top-$M$}
--- the nodes the walk will expand next. A global and a per-query byte
budget cap how much may move. \texttt{install\_top} decides \emph{who
stays} in the window after a fill, not \emph{who the hop may wait for
to score}. Precision is
$\mathrm{scored\textrm{-}from\textrm{-}window}/\mathrm{fetched}$, not
``every fetched page later scored from a host bounce.''

The measured P3 loop still scores from that bounce after
\texttt{PREFETCH\_BATCH} returns~(\S\ref{sec:impl}). That is overlap,
not hide; the rewrite in the evaluation plan splits the two.

We forbid the policies F3 already falsified: synchronous high-coverage
2-hop prefetch, \texttt{install\_all}, and ``fault harder'' loops that
raise queue depth by touching unused pages. Over-promotion is the
failure mode the byte budget exists to prevent.

On corpora where several vectors share a 4\,KB page (low dimension), a
\emph{page-bin / reorder} layout clusters IDs that the walk co-touches so
that one fill admits several useful records. This is layout serving
residency, not a new index family. We report it as a placement option
and show when it helps (small dim) and when it does not (vector $\approx$
page).

\subsection{D3: Entry pin and soft-pin (hot set demoted)}
\label{sec:d3}

Single-query deepening is a bad way to spend a small window (F4, F7).
A 64\,MiB shared LFU set raised hit rate and \emph{destroyed} QPS on a
warm protocol (14.3$\rightarrow$2.4); we do not ship it as D3.
What remains is a tiny hard pin of the entry subgraph ($\le$32\,MiB)
and a hop-decaying soft-pin of recently installed pages. Pinning is
never implicit in a page fault. Cross-query reuse, if it happens, is
because prefetch and \texttt{install\_top} left useful pages in the
window---not because an LFU daemon is competing with search.

\subsection{D4: Hide engine --- lookahead prefetch and continuous batching}
\label{sec:d4}

D4 is the hide engine, not a QPS knob. Offline, we pick the smallest
beam $L$ that meets the recall@$k$ floor. Online, the runtime issues
\texttt{PREFETCH\_BATCH} for pages the \emph{next} hop (and the next
admitted query) will score, then computes distances only on bytes
already in the window. Continuous fetch-level batching keeps a target
device depth $D$ across queries so one pointer-chasing walk does not
collapse to QD$\approx 1$ (Figure~\ref{fig:design-pipe}). Scoring of
already-resident records is never queued behind a fill it does not
depend on. We do not merge the PipeANN binary; its \texttt{cont} path
is the block-device contrast, not this runtime.

\subsection{D5: Observability}
\label{sec:d5}

Every experiment in~\S\ref{sec:eval} is required to report hide
counters first: fraction of full-precision scores whose bytes were
already in the window (\texttt{score\_from\_window}), critical-path
wait on NAND (\texttt{crit\_wait\_ns}), overlap
(\texttt{device\_fill\_ns}/\texttt{wall\_ns}), then QPS at the
iso-recall floor. Promote precision is
scored-from-window$/$fetched. QPS without those counters is not a hide
result.

\paragraph{What we refuse to hide.}
If a module cannot move \texttt{crit\_wait\_ns} or
\texttt{score\_from\_window} in an ablation, it is removed from the
contribution list rather than kept as decoration. An LFU hot set that
raises hit rate and drops QPS is already in that bin.
